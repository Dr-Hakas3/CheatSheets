# SQLインジェクションの概要と確認方法

## 1. 概要

SQLインジェクション（SQLi）は、アプリケーションが利用者の入力をSQL文に安全でない形で組み込み、意図しないクエリとしてデータベースに解釈させる問題です。主な原因は、SQL文と入力値を文字列連結で組み立てることです。

### 主な影響

- 本来許可されていないレコードの閲覧や変更
- 認証・認可処理の回避
- データベースやアプリケーションの可用性への影響
- DB権限や設定によっては、データベース外への影響

### 分類

| 分類 | 内容 |
|---|---|
| 技術分類 | インジェクション |
| 攻撃対象 | SQLを組み立てるアプリケーションとデータベース |
| MITRE ATT&CK | Enterprise: T1190 (Exploit Public-Facing Application)。適用可否は状況に応じて確認 |
| 関連する脆弱性 | CWE-89: Improper Neutralization of Special Elements used in an SQL Command |

## 2. 利用場面

- コードレビューで、入力値がSQL文へ渡る経路を確認する
- 許可された検証環境で、入力による応答差やエラーを確認する
- 修正後に、同じ入力経路がパラメーター化されていることを確認する

## 3. 前提条件

| 項目 | 内容 |
|---|---|
| 対象環境 | 所有または明示的に検証許可を得たアプリケーション |
| 必要な権限 | 対象範囲と許可条件に従う |
| 必要なツール | ブラウザー、開発者ツール、必要に応じてHTTPプロキシ |
| ネットワーク条件 | 検証環境で許可された経路 |
| その他 | 本番データを使わず、影響範囲と停止条件を事前に定める |

## 4. 調査・検証

### 4.1 入力経路の把握

フォーム、URLパラメーター、ヘッダーなど、利用者が制御できる値をアプリケーションがどの処理へ渡すかを記録します。ソースコードを確認できる場合は、SQLの組み立てと実行箇所を追跡します。

### 4.2 応答の比較

検証環境で、通常入力と無害な境界値を用いた入力を比較します。HTTPステータス、応答本文、表示件数、応答時間、アプリケーションログを記録し、入力以外の条件を揃えます。

### 4.3 結果の判断

単一のエラーや遅延だけで脆弱性と断定しません。再現性、アプリケーション側のログ、クエリ構築コードを合わせて確認します。誤検知の可能性も記録します。

## 5. 失敗時の確認

- [ ] 対象範囲と検証許可を確認したか
- [ ] 通常入力との比較条件を揃えたか
- [ ] キャッシュ、レート制限、非同期処理の影響を考慮したか
- [ ] アプリケーションログとDBログを確認したか
- [ ] エラーや応答遅延だけで結論づけていないか

## 6. 検知と防御

### Blue Team：検知

- 入力値に起因するDB構文エラーの急増
- 同一エンドポイントへの不自然な反復リクエスト
- アプリケーションログとDB監査ログの相関

誤検知を抑えるため、単語の出現だけで判定せず、エンドポイント、頻度、応答、ユーザー操作を組み合わせて確認します。

### Green Team：対策

- プレースホルダーを使ったパラメーター化クエリを使用する
- テーブル名や列名など、値として束縛できない識別子は許可リストで制御する
- DBアカウントを最小権限にする
- 詳細なDBエラーを利用者へ返さず、サーバー側で安全に記録する
- 回帰テストで入力処理を確認する
